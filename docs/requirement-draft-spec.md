# 需求草稿字段与人工裁决规范

> 变更 ID：CHG-20261009-REQ-DRAFT-01  
> 版本：v0.2 · 状态：代码已实现；产品评审与浏览器验收待完成  
> 日期：2026-10-09  
> 基线：REQ-001 / TASK-005、TASK-007、TASK-008

## 1. 边界与原则

- AI 生成的是候选草稿，不是已批准需求。分析区必须显示“AI建议，非结论”。
- 用户批准前，候选项不得创建正式开发/测试任务，也不得进入正式需求基线。
- 草稿以 `DRAFT-*` 标识；只有批准时才分配 `REQ-*` 正式编号和 `baselineVersion=1`。已存在的历史 `REQ-*` 编号为兼容旧数据，不回写改号。
- 用户陈述、项目记录、访谈观察和量化/独立佐证分开记录。E0–E4 是项目内来源分级建议，不表示真伪或价值。
- 证据不足时明确保留缺口，不要求 AI 猜测补全。

## 2. 草稿必需字段

| 字段 | 存储键 | 约束 / 说明 |
|---|---|---|
| 用户问题 | `subtitle` | 具体描述目标用户遇到的问题/场景，不把解决方案当问题 |
| 合理性评估 | `rationality` | 说明问题是否值得解决及其依据；推断与事实分开 |
| 价值假设 | `value` | 可验证的用户/业务价值假设，不写成已实现结果 |
| 证据与来源等级 | `evidence`, `evidenceLevel` | 描述现有来源；E0 无可追溯来源、E1 用户陈述、E2 项目产物/使用记录、E3 直接访谈/观察、E4 可重复量化或独立佐证 |
| Kano 候选类型 | `kano` | 魅力型、期望型、基本型、无差异型、反向型或待分析 |
| 分类依据 | `why` | 解释功能/反功能逻辑与目标人群，不能只给类别名称 |
| 置信度 | `confidence` | 0–100 的 AI 判断信心；证据不足时降低，并说明不是概率或用户研究结果 |
| 证据缺口 | `evidenceGap` | 明确仍需回答的问题、样本、记录或验证方式；无缺口时说明依据 |
| 优先级建议 | `priority` | P0/P1/P2，只是建议，不构成范围批准 |

工具输出应保留原始用户输入与 AI 草稿，文档中标识状态及时间。不得输出“已批准/已确认”或相同含义的语句，除非已有人工裁决记录。

## 3. 四种人工裁决

| 动作 | 状态 | 必填 | 结果 |
|---|---|---|---|
| 批准 | `已确认` | 理由（至少 3 字） | 分配/确认正式 `REQ-*` 编号与基线版本，记录人、时间、理由，再排入 PM 拆解队列 |
| 驳回 | `已拒绝` | 理由（至少 3 字） | 记录裁决；不进入基线、不创建任务 |
| 修改后再议 | `待你裁决` | 编辑后的草稿字段、修改理由（至少 3 字） | 保留修改前快照并增加分析/裁决历史；重新进入裁决队列；不创建任务 |
| 挂起待证据 | `挂起待证据` | 当前缺少的证据/理由（至少 3 字） | 保留候选草稿与来源；允许后续补证后重新评审；不进入基线、不创建任务 |

AI 补充调研是一个独立的协作动作，不替代上述裁决，也不更改用户决策权。

## 4. 审计和追溯

每次裁决至少记录动作、操作者、时间、理由、裁决前后的草稿快照和正式基线版本（若已批准）。`修改后再议` 必须保留旧字段快照。裁决、需求包/PRD 记录、项目事件和项目群同步应引用同一候选/正式编号；只有批准动作可以创建 PM 父任务。

需求详情应展示问题、合理性、价值假设、证据来源等级、Kano 候选/依据、置信度和证据缺口。追溯链能够定位裁决历史、关联记忆、任务与文档。没有人工批准记录时，UI 明确显示“未形成正式需求基线”。
