## 需要创始人裁决的问题

1. 你希望首批用户是谁？这款产品首先服务内部自用、个人开发者、小型团队，还是企业研发团队？
2. 用户最重要的“第一价值”是什么：需求澄清与裁决、会话/项目记忆、项目角色执行，还是可追踪的文档和交付？
3. 首版必须覆盖哪些角色？哪些角色可由 PDT/PM/SE 的能力代替？
4. “多个同类型角色”代表多个独立 Agent 并行、同角色冗余成员，还是可供任务调度的候选池？
5. 角色汇报树应否固定为 PDT → PM/SE/PE，PM 管理交付，SE 管理技术任务，还是每个项目自定义？越级消息哪些内容必须回流？
6. Kano 分析是否需要实际问卷/访谈工作流？谁提供用户样本和证据？AI 只能建议还是需要汇总问卷结果？
7. 瀑布、敏捷、混合模式是否需要第一版就自动门禁？希望具体哪些阶段/交付物/角色入场作为门槛？
8. 会议频率范围、议题来源和哪些角色可异步汇报？自动会议是否要考虑成本上限和安静时段？
9. 成功指标的初始基线和试点用户由谁确定？
10. 产品是否会处理企业源码、客户信息或其他敏感数据？部署位置、模型供应商和数据保留要求是什么？
11. Codex / Claude Code 角色是否需要下一阶段直接调用 DevTing 项目工具（经 MCP/受限 API），还是保留“本地改代码、平台 Runtime 写结构化任务与文档”的边界？

已实现的默认边界：本地 SQLite 持续保存到用户删除项目或操作者删除整个数据库；无自动到期清理。项目级 JSON 导出当前不能导入恢复。

## 假设与风险

- 认为方向不清和信息丢失是高频、高成本问题，尚未有用户证据。
- 认为用户会愿意审阅 AI 建议并维护批准门槛，尚未验证其操作负担。
- 认为较多角色 Agent 能提升质量；也可能造成开销、等待、责任不清和信息噪声。
- 高频会议可能导致重复汇报、模型调用成本和通知疲劳；间隔/议程可配置，但成本预算与安静时段仍待确定。
- 结构化文档若过多仍会重现“没人阅读”的痛点，应通过关键决策摘要/角色按需读取验证信息密度。
- 多用户、敏感数据和实时并行写入是本地 MVP 与生产化之间的显著差距。

## 决策记录模板

后续决策应填写：编号、标题、状态（提议/已确认/已撤销）、决策人、日期、背景与证据、候选方案、决定、影响的需求/任务/文档、复核条件。没有决策人的内容保持“提议”或“待确认”。
