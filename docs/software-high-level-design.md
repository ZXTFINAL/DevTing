# 软件概要设计

> 版本：v1.0 · 状态：按仓库现状整理，待系统工程师评审  
> 日期：2026-09-30

## 1. 设计目标

提供可在本地运行的多项目研发协作 MVP，使用 Deep Agents 组织 PDT 主 Agent 与专业子 Agent；以服务端项目状态作为事实来源，把会话、需求、任务、决策、交付文档和事件持久化，使后续对话可按需恢复项目上下文。

## 2. 当前技术组成

- **Web 前端**：静态 `index.html`、`app.js`、`styles.css`，负责工作台视图、交互、项目选择和调用 HTTP API。
- **应用服务**：Python 3.12+、FastAPI；模块集中在 `backend/app.py`。
- **存储**：SQLite，默认 `.data/zhidian.sqlite3`；项目业务状态按项目保存为 JSON，项目、事件和文档快照有独立表。
- **Agent 层**：Deep Agents 主 Agent 与专业子 Agent；模型通过 LangChain OpenAI 兼容接口配置，默认模型值为 `openai:deepseek-flash`。具体可用模型以本地依赖和供应商当前支持为准。
- **配置**：服务端 `.env`；DeepSeek 密钥被映射到 OpenAI 兼容客户端环境变量。密钥不应发送到浏览器。

## 3. 逻辑组件

```text
浏览器工作台
  ├── 项目 / 需求 / 任务 / 文档 / 会议 / 团队 / 消息视图
  └── FastAPI HTTP 接口
       ├── 项目与状态 API ───────────── SQLite project_state / projects
       │                                └─ 项目记忆：事实/决策/证据/假设/风险与来源审阅
       ├── Agent 编排 API ───────────── Deep Agents PDT → 专业子 Agent
       │                                └─ 项目工具：读上下文、分析需求、更新任务/文档、决策、群消息
       ├── 需求计划调度器 ───────────── 批准队列 → PM 拆解 → 角色任务 / 交付文档
       ├── 会议 API / 本地调度器 ─────── 主题议程 → 角色汇报 → PM 纪要/待确认行动项 → 用户确认转任务
       └── 事件、团队关系与文档版本 API ─ project_events / reportingLines / document_versions
                                            └─ 决策审阅与记忆追溯 API
```

## 4. 关键业务边界

- 每个项目拥有独立的项目 ID 与状态 JSON；API 从项目参数定位状态。
- AI 产生建议和 DRAFT 候选项；只有用户批准 API 能把候选转为 REQ v1 正式基线，Agent 工具没有批准接口。拒绝、修改后再议和挂起不建任务。
- 只有“已确认”需求才允许通过任务工具创建关联任务。
- 需求分析可退回到同一条记录继续补充后重新送审；新增/修订候选需求和裁决都进入产品包/PRD正文。
- 任务状态按迁移表校验；完成要求已有验收标准和验收说明，阻塞要求说明原因；变更写入项目群、事件和设计/测试/自测文档快照。
- 角色汇报关系可配置并拒绝循环；该关系进入 Agent 上下文，但不是收件权限或强制路由系统。
- Agent 修改文档前可读取当前正文；写入完整正文并产生文档快照及事件。
- 长期项目事实落入存储，单次 Agent 调用不能只依赖压缩后的对话摘要。
- Deep Agents 的默认 `execute` shell 工具被排除；项目状态变更通过受控项目工具执行。

## 5. 主要数据流

1. 浏览器请求 `/api/state?project_id=…` 获取工作区状态。
2. 用户创建项目时，`POST /api/projects` 建立项目及初始状态和文档骨架，不调用模型。
3. 用户发消息到 `/api/chat`；服务把当前会话最近至多 20 条消息交给对应 Agent，并持久化来回消息。角色私聊结果会在项目群产生简短同步提示。
4. Agent 通过项目工具读取状态与已接受项目记忆，提出/修订候选需求、记录待核实的假设/风险、推进自己负责的任务、写入文档、建议决策或同步项目群；重要写入使用进程内锁，保存时由 SQLite store 记录变更文档快照。Agent 不可把假设直接变成已确认事实。
5. 用户批准需求后，批准接口更改需求状态、创建关联 PM 拆解任务与持久化队列记录、更新产品文档版本并记项目事件；本地调度器接单后调用 PM Agent 生成角色任务、验收标准和文档更新，状态变化写回项目状态。
6. 会议可手动指定主题与议程，或使用项目默认议程定时运行；PDT、活跃任务角色、SE、QA 依序汇报，PM 返回结构化纪要、决策请求、交付顺序和 AI 行动建议。确认行动建议的 API 会再次验证已确认需求、角色和验收标准，再幂等建立任务；建议本身不会自动建任务。
7. AI 提出的项目决策进入待审阅状态；用户通过专用 API 填写理由并采纳、拒绝或搁置。审阅写入版本历史、决策台账、项目群和事件。采纳不会代替需求基线审批，也不会自动派生任务。记忆追溯只扫描结构化引用和文档内容，不把聊天逐字记录作为证据。
8. 用户通过团队配置 API 更新角色人数与专属提示词；服务端校验角色 ID、人数和提示词长度并持久化配置，汇报关系由独立 API 做环路校验。全量状态提交保留这三项服务端配置，避免陈旧页面覆盖。

## 6. 可扩展方向

将状态 JSON 中高频实体规范化为关系表；引入可靠事件/任务队列和实时 UI 更新；完善 Agent 层级消息路由、权限和成员身份；用文档差异与引用实现轻量记忆检索；把方法流程抽象为可配置阶段门和角色入场策略；为备份、冲突处理、模型调用审计与失败恢复提供独立服务边界。

## 7. 质量与风险

- 当前为单用户本地服务，没有认证和服务端用户级授权。
- 关键接口使用进程内锁；整份状态写入会保留服务端权威的需求、记忆、决策、会议、任务、文档和角色配置，但一般字段仍缺少乐观版本控制。多进程/多 worker 及多人并发编辑仍未解决，不能按多人生产环境使用。
- 会议在本地应用进程内调度，进程停止时定时执行不会运行；没有任务队列级恢复。
- Agent 模型质量、延迟、成本和可用性取决于外部服务，不能视为系统保证。
- 当前版本快照是全文副本，暂未做差异/保留策略。
- `.data/` 与 `.env` 是本地运行敏感状态，需有明确的备份和访问控制策略。
