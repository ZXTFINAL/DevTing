# 产品愿景与创始人构想

> 文档状态：初始基线 v0.5 · 待创始人评审  
> 建立日期：2026-09-30  
> 信息来源：创始人在项目对话中的原始构想。本文中的市场判断、价值假设和未来能力不代表用户研究结果或已批准范围。

## 一句话愿景

让 AI 原生研发团队围绕清晰、经人确认的需求和可追溯的项目事实持续交付，使团队不必靠漫长聊天、人工补写大量文档或反复猜方向来推进软件项目。

## 创始人描述的问题

创始人观察到，当前许多 AI 开发工具把重点放在通用 runtime 和更强的大模型上；但真实研发中，主要阻力常常出现在代码之前和代码之外：需求与产品方向尚未明确，重要会话信息在压缩或交接中丢失，项目成员需要维护繁杂文档，而自动生成的文档又可能太长而无人阅读。方向偏移后，开发活动看似很多，实际效率却下降。

这是创始人的问题假设，尚未通过目标客户访谈、数据或市场研究验证。后续需要定义目标用户、发生频率、现有替代方式和可量化影响。

## 目标与价值假设

- **需求先于任务**：AI 协助澄清问题、检查合理性并给出分类和证据；只有用户确认纳入范围的需求才能成为研发基线并派生正式开发任务。
- **把项目事实放在对话之外**：需求、决定、交付物、进度、责任和来源保存在项目空间中，角色按需读取；对话摘要不应成为唯一记忆载体。
- **文档为决策和交付服务**：每次有意义的范围、设计或验证变化都更新相关交付物，留下版本和变更原因；文档可读、短而完整，并显示未决事项。
- **团队分工受项目节奏约束**：PDT、PM、系统、产品、UI、研发、测试和运维角色按所选方法与交付阶段入场。
- **HITL 保留关键控制权**：AI 给建议并说明依据，用户负责产品方向、需求基线和重要取舍。

## 需求分类：Kano 假设

本项目使用 Kano 五类作为候选分析框架：

| 类型 | 初步解释 | 需要验证的问题 |
|---|---|---|
| 基本型 | 不具备会明显不满；具备通常只消除不满 | 缺少该能力是否会导致用户拒绝产品或强烈抱怨？ |
| 期望型 | 能力越好，满意度通常越高；不足会带来不满 | 更快、更准或更方便会带来多大程度的满意变化？ |
| 魅力型 | 具备时可能明显惊喜；缺少时通常不会造成同等程度不满 | 用户是否未预期该能力，但看到后认为有明显价值？ |
| 无差异型 | 有无对满意度影响很小 | 目标用户是否在真实场景中注意或使用它？ |
| 反向型 | 部分用户可能不希望具备该能力 | 哪些人群会因该能力而更不满意？ |

分类是待验证判断，不应只由模型凭措辞下结论。推荐通过功能性与反功能性成对问题、开放式追问、目标人群样本及场景证据辅助判断；记录依据、样本、置信度和反例。当前实现支持 AI 候选分类、置信度和用户裁决流程，尚未内置完整的问卷采集和统计分析。

方法来源：Kano 等人在 1984 年提出将质量属性按其满足/不满足时对满意度的影响进行二维分类；后续方法研究说明实际问卷会为每个属性分别询问功能存在与缺失时的感受，并结合评价表归类。可参阅 [Kano et al., “Attractive Quality and Must-Be Quality” (1984)](https://www.jstage.jst.go.jp/article/quality/14/2/14_KJ00002952366/_article) 与 [Empirical research on Kano’s model and customer satisfaction](https://pmc.ncbi.nlm.nih.gov/articles/PMC5584930/)。问卷中可能出现的可疑/矛盾回答应提示复核，不作为额外的用户需求类别。

## 原始构想整理

1. **AI 参与需求分析**：通过 HITL 快速判断需求是否合理、需求类型以及是否可能是魅力型需求；需求分析本身成为 AI 工作的一部分。
2. **阶段性交付和持续文档**：AI 在有意义的步骤后更新产品需求包、PRD、软件概要设计、详细设计、测试大纲、自测大纲等项目文档。开发按已确认需求清单推进，不再无目标地堆任务。
3. **项目角色和责任**：设置 PDT 经理、项目经理、系统工程师、产品工程师、UI 工程师、前端、后端、大数据、算法、测试、部署与运维等角色；一个角色可以有多名成员，各角色有专属提示词和任务边界。
4. **管理和汇报关系**：PDT 经理直接与用户沟通方向、节奏、产品形态、需求和方案。PM 管理需求到开发、测试、UI 和交付任务的追踪。系统工程师把控架构和技术方向，并与开发人员协调变更。其他角色向对应上级汇报；越级沟通的重要结论应回传相关上级及同事。
5. **项目会议**：按项目配置的节奏（例如每五分钟）开展会议，明确议题；角色在执行任务期间提交进展、风险、阻塞和决策请求，PM 组织纪要、行动项和交付物顺序。
6. **可操作的项目工作台**：先以 Deep Agents 架构实现可检视的版本；用户可以和单个角色对话，也可以向项目群发言。项目群用于同步共同事实，角色专属会话用于定向协作。
7. **多种研发模式**：瀑布式、敏捷式及后续可扩展的方法，应决定阶段门、角色入场时机与产物节奏，而不只改变一个界面标签。
8. **项目树形路线图**：主页以阶段、需求、任务和交付物组成可展开的 Roadmap；节点可查看当前状态和持续事件进度，项目并行上限与单任务串/并行策略均可配置，并在任务启动时由服务端约束。
9. **不静默等待用户**：当 PDT 或项目角色提交待裁决需求/决策时，工作台主动提示用户进入详情；用户始终是需求基线和重要取舍的最终裁决者。
10. **按角色选择 Runtime**：角色可使用平台项目 Agent，也可连接用户本机 Codex 或 Claude Code 子 Runtime；角色报告回到项目群，项目事实和正式交付物继续留在统一项目空间。

## 当前验证状态

- **已实现的本地 MVP 闭环**：项目创建与隔离、9 类文档骨架和初始构想保留、Deep Agents 主 Agent/专业子 Agent、需求分析及 Kano 候选、用户确认/拒绝/修改后再议/挂起待证据/退回补充分析、确认后的关联任务创建及验收状态迁移、角色单聊与项目群、审计事件通知、文档全文/版本恢复、Markdown 项目包与 CSV 需求导出、可编辑汇报树，以及可配置的手动/定时会议基础。
- **本轮已接入的能力**：项目 Markdown 内容渲染从聊天扩展到文档、需求、任务、记忆、决策、会议、追溯和路线图进度页面；角色级 Runtime 可选平台、Codex CLI 或 Claude Code CLI，PDT 委派和角色报告同步会按 Runtime 配置路由。隔离假 CLI 子进程测试覆盖报告同步和密钥边界；服务启动会标记失败并清理进程崩溃时遗留的会议运行状态。真实供应商 CLI 与真实浏览器全流程仍需后续评估。
- **仍属于构想或部分实现**：多用户权限和团队协作、逐级消息实际派发及收件确认、多个 Agent 长时并发运行、不同方法的完整阶段门与角色入场自动化、问卷式 Kano 研究和客户证据分析、自动会议定时器可靠队列和中断发言续跑、聊天变化自动检查所有下游文档、文档差异和实时共同编辑。
- **重要边界**：当前交付版适合单用户本地试用，敏捷/瀑布/混合配置会保存且影响节奏说明，但尚未对整个软件流程实施强制阶段门。旧版默认工作区保留早期原型历史数据，界面与 Agent 上下文均标注来源待核验；历史聊天中的研究描述、会议表述和需求状态不能自动视为客户证据或已确认范围。新建项目使用空白业务基线。

## 下一步要验证

1. 首要用户是独立开发者、小型产品团队、AI 应用创业团队，还是企业研发团队？
2. 哪类项目最容易感受到“需求方向不清”和上下文丢失的成本？
3. 用户愿意把哪些决策交给 AI 建议，哪些必须由人批准？
4. 项目文档应如何做到简洁、足够可读，又能支撑不同角色按需工作？
5. 会议需要五分钟级的高频同步，还是事件触发、每日/阶段性同步更合适？
6. 首版应验证“需求到任务追踪”、“项目事实记忆”还是“多角色协作”中的哪一个核心价值？
