# 产品需求文档 PRD

> 版本：v3.1 · 状态：产品草案，待 PDT / 创始人评审  
> 日期：2026-10-13 · 依据：[产品需求包](product-requirements-package.md)

## 1. 背景与目标

产品要降低研发团队在方向澄清、上下文延续、交付追踪和跨角色同步上的协调成本。AI 应参与需求和交付工作，但范围决策权留给用户。本文描述期望的产品行为；“当前实现”指出工作台已存在的基础，不能视为完整生产能力。

## 2. 用户和角色

- **项目发起人 / 用户**：提出想法、回答澄清问题、审查证据、批准需求基线并决定方向。
- **PDT 经理 Agent**：主要用户入口，综合方向、优先级、风险和专业意见，给用户可执行建议。
- **项目经理 Agent（PM）**：拆解并追踪任务、依赖、进展、风险、会议行动项和交付物。
- **系统工程师 Agent（SE）**：维护系统边界、架构和技术决策；评估技术变化影响并与研发角色协调。
- **产品工程师（PE）**：澄清场景、范围、价值证据、需求定义和验收条件。
- **UI、前端、后端、大数据、算法、QA、运维角色**：分别交付交互、客户端、服务端、数据、算法、验证与发布运维成果。
- 每类角色允许配置多个 Agent/成员；后续需要明确分工分配、共享上下文和权限模型。

## 3. 端到端旅程

### 3.1 创建项目

用户提供项目名称、问题描述/初始想法、产品形态和开发模式。系统创建隔离的项目空间、需求和任务空列表、角色对话空间以及项目交付物骨架。创建项目不应自动调用模型；用户主动进入 PDT 会话后开始需求澄清。初始描述保存为来源事实，不自动批准为需求。

**验收标准**：新建项目后可切换并重开；新项目没有从其他项目继承的业务数据；项目名称、初始想法、产品形态和开发模式可见；文档目录包含产品、设计、质量、运维、愿景和待确认事项交付物。

**当前实现状态**：隔离 SQLite 浏览器流程通过创建并刷新检查；项目保持需求/任务为空，生成 9 份文档，初始构想留在《创始人构想与产品愿景》中并在空项目首页以 Markdown 显示；“开始需求澄清”进入 PDT 会话，不自动调用模型。该检查使用合成项目，不修改默认项目；后续需求裁决到任务/验收的浏览器闭环仍待验收。

### 3.2 需求提出与 HITL 分析

用户可从需求表单或 PDT 对话提交需求。PDT 识别问题、目标用户、场景、替代方案、价值假设、优先级、风险和缺失证据；需要专家时委派 PE、SE、UI 等角色。PDT 将证据、假设、推荐、Kano 类型候选和置信度明确分开。

Kano 分类候选为基本型、期望型、魅力型、无差异型、反向型或待分析。理想分析结合功能/反功能提问及目标人群证据。若信息不足则状态为“分析中”，提出少量高价值问题；若已具备初步依据则进入“待你裁决”。

分类依据参见 Kano 等人 1984 年原始论文及关于 Kano 方法的实证综述：[原始论文](https://www.jstage.jst.go.jp/article/quality/14/2/14_KJ00002952366/_article)、[问卷分类方法综述](https://pmc.ncbi.nlm.nih.gov/articles/PMC5584930/)。矛盾/可疑问卷回答应回访或标为数据质量问题，不应强行归入五类之一。

**验收标准**：用户能看到合理性、分类理由、证据、来源等级、置信度、价值假设和未决问题；不确定性不会被隐去；AI 分析明确标为“AI建议，非结论”；用户可确认、拒绝、修改后再议或挂起待证据，且需填写理由；只有用户确认才改变正式基线。当前 E0–E4 来源分级是项目内部建议：E0 无来源、E1 用户陈述、E2 项目产物/使用记录、E3 直接访谈/观察、E4 可重复量化或独立佐证，不宣称是通用标准或真实性概率。

**当前实现**：候选项使用 `DRAFT-*` 编号，详情展示必要分析字段和“AI建议，非结论”。支持确认、拒绝、修改后再议、挂起待证据，裁决理由必填；修改保留前后快照并增加草稿版本。只有确认会分配正式 `REQ-*` 编号和 `baselineVersion=1`，记录用户裁决并排入 PM 拆解。拒绝、修改和挂起不派生任务；补充分析可从待裁决或挂起状态返回 PE。变更写入项目文档、事件、项目群和追溯历史。隔离临时项目上真实 Deep Agents 生成过一条待分析 DRAFT，批准前没有任务；该样本不代表分类质量已通过。完整多用户身份/权限仍未实现，因此“用户”目前是本地工作台操作人。页面与服务流程的完整验收仍需按测试大纲执行。

浏览器离线时，需求裁决和草稿修订进入本地待同步队列；服务端恢复后自动重放，以服务端状态为准，并通过 action ID 避免重复应用。正式编号和 PM 任务只在批准已同步到服务端后生成。该队列限于同一浏览器，不涵盖离线任务编辑或跨设备同步。

### 3.3 需求批准与任务拆解

用户批准候选需求后，系统记录裁决人、时间和说明；PM 将需求拆为产品、UI、研发、测试、发布等必要任务，任务都关联需求并包含验收意图、负责人角色、状态和依赖。

**验收标准**：模型工具不能批准需求；任何未批准需求都不能创建正式研发任务；任务可追溯到来源需求；缺少验收条件的任务不能标记为可交付。

**当前实现**：人工确认后创建正式需求基线，再创建与需求关联的 PM 拆解任务并写入项目内队列；单进程后台调度器会调用 PM Agent 生成角色研发/测试任务、验收标准、适用文档修订和项目群摘要。队列与状态保存在 SQLite 项目 JSON 中，服务重启后会续跑；没有模型时任务保留在队列，执行失败则标记阻塞并允许用户从需求详情重试。一个临时数据库的真实 Deep Agents 验收样本在批准后完成队列执行并生成 3 条关联任务；尚未评审任务内容质量。在线界面每 5 秒拉取新进度。每个新增任务要求填写验收标准。看板支持按需求与负责人过滤，以及“待开始 → 进行中 → 评审中 → 已完成”与阻塞分支；完成必须有验收标准和验收说明，阻塞必须有原因。任务状态历史写入项目事件、项目群和设计/测试/自测文档快照。

### 3.4 专业协作和变更控制

PDT 可调用专业 Agent。角色先读取项目状态与相关文档，再进行职责范围内分析；遇到影响目标、范围或架构的变化，向相应负责人提出建议，并在项目群同步共同需要知道的结论。越级消息应保留请求来源、处理角色、需通知的上级和关联工作项。

**当前实现与限制**：MVP 提供可编辑、校验无循环的汇报关系树，角色人数（每类 1–12）和专属系统提示词通过服务端接口保存，并把关系与提示词放进后续 Agent 构建配置；用户可和全部 11 种角色单独对话，直聊结果/重要进度会在项目群留痕。角色人数是同类 Agent 配置数量，不是具备独立账号的真实成员。当前还没有强制收件确认、主题订阅、私聊权限或逐条按经理路由的组织消息系统。

### 3.5 文档与长期项目记忆

工作台提供产品需求包、PRD、概要设计、详细设计、测试大纲、自测大纲、部署运维方案、创始人愿景及决策/待确认事项。重要变更由相关负责人读取现状后写入完整正文，并记录变更摘要、版本、更新人和历史快照。文档展示状态、负责人、更新时间和未决事项。恢复历史版本必须另存为新版本。

项目另有“项目记忆”视图，保存事实、决策、证据、假设与风险，并记录文字来源及可选需求/任务/文档关联。用户录入项标为“用户提供”；Agent 只能记录待核实假设或风险，用户审阅后才能标为“用户确认”并纳入角色上下文。已取代条目保留历史，不再作为当前上下文返回。记录和审阅会同步到决策台账、项目群、事件和项目包导出。
超出默认上下文窗口的旧条目可按关键词检索，返回来源、审阅状态和关联编号，以便角色需要时恢复精确历史。

项目记忆记录还保存建议证据等级、AI 信心（仅对 AI 提议适用）、审阅人、版本号、200 字以内变更摘要和逐次历史；旧记录迁移时以 E0 标记且不推断原始来源强度。项目记忆视图展示由当前需求、任务、决策、风险和文档状态生成的“必读摘要”，支持单独导出 Markdown。摘要每次打开时按项目当前状态计算，不作为独立事实来源。

每条记忆可查看一跳追溯：直接关联的需求/任务/文档、明确引用其编号的决策/交付文档/会议记录，以及通过同一需求关联的其他任务（标明为间接关系）。聊天消息和逐字发言不参与事实引用索引。

需求详情的追溯入口返回人类裁决、关联决策建议、显式链接的项目记忆、相关任务、文档命中项及澄清/分析历史。项目记忆可以打开一跳追溯，查看直接关系、明确引用编号和通过同一需求关联的任务；聊天内容不作为事实引用。

AI 提交的项目决策建议进入独立决策台，用户需填写理由后可采纳、拒绝或搁置。系统保存提议角色、审阅人、时间、版本和前后状态，并同步项目群与决策台账。采纳建议不会代替需求基线裁决，也不自动派生任务。

**验收标准**：刷新/重启后正文仍存在；变更产生快照；快照可预览和恢复；角色可按需读取单份文档；未验证结论明确标记；文档索引与项目内文档一致。

### 3.6 角色会话与项目群

用户可向 PDT 或专业角色私聊，也可在项目群发布信息。私聊产生的关键发现、决策请求和阻塞应按明确规则共享给相关同事和上级；群组保留统一的消息来源和时间。每种消息关联项目、角色、可选需求/任务/文档。

**当前限制**：会话和项目群保存在同一项目状态并按角色区分。角色私聊会产生进展通知，但还没有主题订阅、确认回执与权限隔离的消息路由。

### 3.7 项目会议

用户可手动发起会议或启用定时会议并设置节奏、默认议程。手动发起时填写本轮主题和议程；按 PDT、活跃任务相关角色、系统工程师和测试工程师顺序汇报完成、下一步、风险/阻塞和需要决策。PM 生成结构化纪要、用户裁决请求、交付顺序及带负责人、已确认需求关联和验收标准的行动建议。用户可暂停自动会议。

**验收标准**：会议保存主题、议程、角色发言、出席者、PM 纪要、裁决请求和交付顺序，并同步简明纪要到项目群和交付文档。行动建议明确标注为 AI 建议；只有用户明确确认且行动项关联已确认 REQ、有效交付角色和验收标准时，才创建任务；重复确认不重复建任务。角色/PM 失败应留下可见失败状态并清除运行中标记。手动/自动会议需要 Deep Agents runtime，自动会议由本地单进程 scheduler 执行。

**当前验证状态**：会议纪要解析、人工确认门禁和重复确认幂等已纳入临时 SQLite 集成验收；新增服务启动测试确认崩溃前留下的“进行中”会议会转为失败、保留已保存发言、清除运行标志并幂等重排下一轮。真实模型输出、浏览器会议操作和定时 scheduler 的实际触发仍未由该验收证明。详见[闭环测试记录](test-report-2026-10-13-closed-loop.md)。

### 3.8 研发模式

- **瀑布式**：按阶段门推进；需求与设计基线评审后才开放实施，实施完成后进入系统/验收测试和发布。
- **敏捷式**：以经确认的需求为积压项，按迭代选择范围；设计、开发和验证按小批次并行；每个任务仍必须有清楚验收标准。
- **混合式**：外层保留立项、架构、安全/发布阶段门，内层使用迭代交付。

以上为流程目标。当前实现共享需求追踪和看板说明，未自动强制完整阶段门或角色入场条件。

### 3.9 项目导出与删除

工作台支持导出完整项目 JSON，包含项目信息、当前状态、会话、审计事件和所有文档版本；不包含服务端环境变量或模型密钥。文档页仍可导出便于阅读的 Markdown 项目包，需求页可导出 CSV。JSON 当前用于数据移交和留存，不支持直接导入恢复。

非默认项目可在项目选择器中删除。删除对话会提示用户先导出，并要求输入项目全名确认；服务会删除项目状态、消息、事件和文档版本。默认项目受到保护。当前没有自动保留期限、回收站或软删除，手动删除后不能从本应用恢复。

**当前实现与限制**：项目 JSON 导出和单项目精确名称确认删除已接入，临时 SQLite API 检查通过；浏览器操作仍待人工验收。整个本地数据库仍应定期备份，Markdown/CSV 不替代数据库备份。

### 3.10 项目树形路线图与并行控制

项目总览展示从方向澄清、HITL 需求基线、PM 任务拆解、系统/交互设计、开发集成、测试验收到部署运维的 PDT 流程。路线图可展开到需求和任务，并链接阶段文档。用户点击阶段、需求、任务或文档时查看当前状态、责任角色、验收标准、阻塞和最近的项目事件。

任务可配置串行或允许并行；项目配置最大并行任务数。任务从待开始进入进行中时，服务端检查上限，并确保串行任务不会与其他进行中任务并行。用户降低上限时，不能低于当前正在执行的任务数。PM 计划仍按已确认需求拆解，依赖信息由计划交付记录提供。

Agent 图执行步骤与正式项目状态事件通过 SSE 发送，供路线图显示实时进展。事件流断开时客户端自动重连；当前任务状态仍以项目 SQLite 状态记录为准。需求/项目决策等待用户裁决时，工作台主动弹出待办入口；弹窗只打开详情，不替用户执行批准。

**验收标准**：需求节点能显示其关联任务；并行上限和单任务串/并行策略经 API 持久化；并行超限、串行冲突和不合理降限均被服务端拒绝；任务/Agent 新事件在路线图节点详情内可见；SSE 断开可恢复；待确认需求能主动提示并须用户亲自裁决。

**当前实现状态**：本地 MVP 已加入七阶段 PDT 流程、由需求/任务/文档状态派生的路线图树、节点详情、SSE 事件面板、项目并行上限和任务串/并行 API/UI，以及待用户裁决的主动提示。浏览器已检查路线图与节点详情，隔离 SQLite API 场景已核验并行上限和串行互斥；真实 Agent 多步骤事件流、断线恢复、长项目易用性和待办弹窗交互仍未完成端到端验收。多实例部署和多人编辑冲突控制不在本地 MVP 保证范围内。

### 3.11 项目内容的 Markdown 呈现

项目总览中的方向描述/会议摘要/必读摘要、文档卡片描述/正文/版本预览、需求列表与分析、项目记忆、决策建议、会议纪要/发言、路线图节点详情、追溯内容、任务验收/阻塞说明和项目事件摘要中的 Markdown，使用统一的安全渲染器呈现。支持 ATX / Setext 标题、段落、嵌套列表（含任务清单）、引用、表格、围栏代码（反引号或波浪线）、行内代码、强调、删除线、分隔线、自动链接和图片；原始 HTML 作为文本处理，链接协议限制为 `http`、`https` 和 `mailto`，图片仅允许 `http` / `https`。结构化消息载荷转换为可读 Markdown / JSON 文本。表单输入区仍保留 Markdown 源文，项目导出仍生成 Markdown 文件。

**验收标准**：同一条 Markdown 在聊天、文档和详情页面以一致的语法显示；版本预览与当前文档正文相同；危险 HTML 和链接不会执行；代码和宽表格可滚动查看。

**当前实现状态**：前端统一渲染器已接入项目内容视图，覆盖聊天、列表、摘要、路线图、文档、会议、记忆、决策和追溯；支持图片、裸链接、Setext 标题、波浪线代码围栏和结构化消息载荷，并修复文档骨架中的嵌套段落。2026-10-13 在独立临时 SQLite 浏览器中核验首页构想、创始人愿景文档和项目群消息：标题、行内格式、嵌套列表、表格、代码块和引用均形成正确语义节点；原始 `<script>` 被转义、`javascript:` 链接未生成可点击锚点。其他内容视图和新增语法仍需逐页浏览器回归；详见[Markdown 与 Runtime 浏览器核验](test-report-2026-10-13-markdown-runtime.md)。

### 3.12 每个角色可选本地子 Runtime

用户可以逐角色选择平台 Deep Agents、Codex CLI 或 Claude Code CLI，并配置供本地 CLI 使用的绝对工作区路径。直接角色对话、会议角色发言以及 PDT 的专业角色委派均按该角色配置路由；角色报告保存在角色会话和项目群。平台 Runtime 保留 DevTing 项目工具，可读写需求、任务、记忆、决策和项目文档。外部 CLI 复用本机安装与登录，以本地工作区处理代码；平台向其提供裁剪后的项目上下文，但不授予 DevTing SQLite 工具，因此不能宣称已直接修改项目任务、需求或文档。CLI 缺失、未登录、目录不可访问或运行超时时应返回可见错误，不静默回退到另一个 Runtime。

**验收标准**：Runtime 选择按项目和角色持久化；外部 Runtime 每次只在用户配置的工作区启动，使用无 shell 子进程调用与有限时长；Codex 使用 `workspace-write` 沙箱，Claude Code 使用 `acceptEdits` 模式，不使用跳过权限确认选项；平台创建的 DeepSeek key 不传给子进程；PDT 委派报告进入角色会话和项目群；运行状态和错误可见。外部 CLI 的工具权限、账号与计费由本机 CLI 配置决定。

**当前实现状态**：团队设置、项目状态持久化、健康状态探测、Codex/Claude Code 子进程路由及 PDT 委派入口已接入；团队页逐角色标出当前 Runtime，并展示平台、Codex、Claude Code 的状态和逐角色配置入口。2026-10-13 临时浏览器核验确认 FE 配置可选三种 Runtime，临时服务如实显示平台等待模型配置、Codex 命令可用、Claude Code 未检测；没有保存设置或启动 CLI。隔离 API 测试和假 CLI 子进程测试覆盖配置持久化、受限参数、报告/群组同步、进度事件和密钥剔除。真实供应商 CLI 的登录、输出格式、权限与代码修改仍待验收；外部运行时没有 DevTing 项目数据库工具桥接，需由平台工作流写入结构化项目产物。详见[Markdown 与 Runtime 浏览器核验](test-report-2026-10-13-markdown-runtime.md)。

## 5. 非功能需求（目标草案）

- **可恢复性**：本地 SQLite 状态持久化；业务文档有历史快照；错误不能静默覆盖文档。
- **可审计性**：需求批准、任务建立、文档变化、消息和会议留下项目内来源记录。
- **隔离性**：项目之间的数据和会话完全隔离；未来多用户时需要用户/组织级权限。
- **安全性**：密钥仅由服务端环境变量读取，不写入 SQLite、前端、日志或文档；Agent 运行面收敛到必要工具。
- **可理解性**：AI 结论展示依据、不确定性和待用户决策，而不是伪装成已验证事实。
- 性能、可访问性、备份保留周期和服务可用性目标待通过用户场景确认。

## 6. 错误和边界流程

- 模型未配置或调用失败：允许浏览和保存已有状态，明确报告 AI 不可用；不得假装生成真实 Agent 结果。
- 项目文档不存在：角色工具返回错误，不创建隐式替代文档。
- 需求证据不足：保持分析状态并提出问题，不强行定 Kano 类别或批准。
- 用户拒绝需求：保留裁决和原因；不产生开发任务。
- 并发编辑/会议：当前本地 MVP 尚缺细粒度并发冲突控制，应显示限制并避免宣称多人安全编辑。
- 版本恢复：将快照内容复制为一个新的当前版本，保留旧历史。

## 7. 首版验收建议

以真实的一个小型项目验证：项目创建与隔离、PDT 澄清并留下可读依据、用户批准前无正式任务、批准后形成追踪完整的任务、文档版本可恢复、角色总结能被团队看见、用户能够用简短页面理解当前方向和阻塞。试点对象和定量门槛待确认。
